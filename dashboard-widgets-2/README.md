# Simple dashboard widgets — варіант 5

Навчальний React + Vite проєкт для предметної області «Космічні запуски», майбутнє джерело — Launch Library 2 (`ll.thespacedevs.com`).

**Усі місії, агенції, ракети, дати й показники є mock-даними. Реального API-підключення немає.** Дата демонстрації зафіксована на 12.10.2026 для відтворюваних KPI.

## Запуск

Потрібен Node.js 20.19+ або 22.12+ та npm.

```sh
npm ci
npm run dev
```

Відкрити адресу, яку покаже Vite. Для перевірки й виробничої збірки:

```sh
npm test
npm run check-render
npm run build
npm run preview
```

Автономний перегляд після збірки:

```sh
npm run export-preview
```

Створений `preview.html` містить CSS і JavaScript всередині файла. Його можна відкрити в браузері без сервера й без зовнішніх залежностей. Основний проєкт залишається Vite-проєктом із окремими компонентами.

## Реалізовано

- `KpiCard`: три екземпляри з різними props — найближчий запуск, проведені запуски за 2026 рік, заплановані місії.
- `Counter`: локальне значення 1–30, кнопки збільшення/зменшення, скидання до 10. Це демонстрація налаштування майбутнього `limit`; зараз список не запитується й не обрізається.
- `Toggle`: локальна світла/темна тема секції, `useState`, умовне відображення, доступний `role="switch"`.
- `FilteredList`: таблиця з семи mock-місій, controlled select статусу, stable keys і порожній стан для статусу без результатів.
- `DashboardLayout`: спільна оболонка, композиція через `children`.

```text
src/

  main.jsx
  styles.css
  components/
    DashboardLayout.jsx

  utils/launches.js
test/
  widgets.test.js
  launches.test.js
scripts/export-preview.mjs
```

## Організація даних і стану

`dashboard.js` зберігає локальну відповідь зі структурою `count`, `next`, `previous`, `results`. Місія містить `id`, `net`, `status`, `mission`, `rocket.configuration`, `pad`, `launch_service_provider`.

`App` отримує модель і передає її у віджети через props. Віджети не імпортують дані. KPI не має стану. Значення лічильника, перемикач та вибраний статус живуть у відповідних компонентах. Спільного інтерактивного параметра між віджетами немає, тому зайве підняття стану в `App` не потрібне.

Зміни стану виконуються через setter; лічильник і перемикач використовують functional updates. Фільтрація та підготовка списків створюють нові масиви. Використано `key={id}`, а не індекс масиву.

## KPI і обмеження mock-моделі

Найближчий запуск обирається з майбутніх записів Go/Hold. KPI «Проведено у 2026» рахує завершені записи поточного демонстраційного року, не включає майбутні запуски й архівний запис 2025 року. Зміни `+1` і `+2` є заданими демонстраційними показниками щодо умовної попередньої вибірки.

Статуси й поля моделі охоплюють лише випадки цієї лабораторної. Перед реальним API-підключенням потрібні повна обробка статусів, nullable-полів, пагінації, точності дат і помилок запиту.

## Для захисту

1. Показати, як один `KpiCard` рендериться тричі через `map`.
2. Збільшити й зменшити лічильник, досягти межі, натиснути «Скинути».
3. Увімкнути й вимкнути темну тему секції.
4. Вибрати «Готовий»: 2 із 7; «Успішний»: 4 із 7; «Відкладений»: 1 із 7; «Невдалий»: порожній стан; «Усі статуси»: 7 із 7.
5. Пояснити, чому перемикач і фільтр мають незалежний локальний стан.

Графік запусків за агенціями, дрілдаун місія → ракета/майданчик/статус і реальне завантаження API залишено для наступних лабораторних. Дані для цих розширень уже передбачені в mock-моделі.

## Перевірено під час підготовки

Виробнича збірка Vite й п’ять тестів логіки пройшли. Окремо перевірено початковий рендер React. Візуальний браузерний прогін у середовищі підготовки не підтверджено; сценарії ручної перевірки наведені вище.
